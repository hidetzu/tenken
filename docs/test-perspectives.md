# TEST-PERSPECTIVES — what "works" means

What it takes to say it "works" is decided before the implementation.
The scope is [`design.md`](design.md) §0.3 (v0.1.0).
Nothing undecided is left here (the opening of [`design.md`](design.md)).

---

## 1. Ground rules for tests

- **Tests do not reach the external network.** Tests run against real sites are not run in CI (they are kept separately, as checks run by hand)
- HTTP / HTTPS test servers are started inside the test. Pages, statuses, redirects, headers and delays can be assembled per test
- Certificates are made inside the test (a self-signed CA, and server certificates with varied validity, host names and chains). **No certificate with an expiry is kept in the repository as a file** (some day it expires and the test breaks)
- The test can substitute the time (so the boundaries of "days left" are tried without depending on today's date). This includes the time passed to certificate verification
- tenken needs a way to trust the CA of the test's HTTPS server (an option that names a CA to trust. [`design.md`](design.md) §0.3)
- The shape of the output (the human-readable form, JSON) is compared against expected-value files (golden). The order is a fixed order

## 2. Shared behaviour

### 2.1 Exit codes

**The source of truth for the values and their meaning is [`cli-reference.md`](cli-reference.md) §4.** The values below are written to name the situations tested. If they disagree with cli-reference.md §4, cli-reference.md is right and this file is fixed. What is tested:

- **Every row** of the table in cli-reference.md §4 **has a test that ends with that value** (each of 0 / 1 / 2 / 3)
- With only warnings, 0; with `--fail-on warn`, 1
- No CA read from the OS trust store and no `--ca-file` is 2 (going on would make every certificate untrusted). On macOS / Windows it is judged only when `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, because only then does Go read the trust store from files; otherwise the OS verifier decides and an empty pool says nothing
- With only findings that were `--ignore`d, 0 (they do not count toward the exit code)
- A start URL with 4xx / 5xx is 1 (`links.broken`, and the checks that need the crawl are `skipped`); a DNS, connect, TLS or timeout failure is 3. **These two are never mixed up**
- Even if the start URL's certificate has expired, if it can be connected to it is 1 (`cert.expired`). Not 3
- A redirect loop or a broken `Location` at the start URL is 1; if the redirect target cannot be reached, 3; 429 even after a retry is 3 (`rate-limited`)
- A redirect of the start URL's own chain into a private address of another host is 3 (`private-address`), whether the start host is public or local (`localhost` → `127.0.0.1`, an intranet name → another intranet name): the reason names the URL not connected to and says tenken's safety policy kept it from being fetched, `findings` and `skipped` are empty, and `summary.not_fetched.private` is 1. The same stop in the crawl, robots.txt, a sitemap or the `http://` probe is not 3
- When the start URL's own host, whose first connection found a public address, resolves to a private address within the start URL's chain (a redirect to another path on the same host, or the retry of a 429), it is also 3 (`private-address`), with a different reason: it names the URL, says the host resolved to a private address during the run and that tenken's safety policy does not connect to it, and says to check why the host name's resolution changed. The reason for another host is not used for it. When the first connection to the start URL went through a proxy (not checked, so not local) and a later URL of that host, not through the proxy, resolves to a private address, it is also 3 (`private-address`) with a third reason: it names the URL, says it resolved to a private address and that the first connection went through a proxy so tenken did not check whether the start host is local, and says to use the proxy the same way for every URL of that host (`NO_PROXY` and the like)
- An unknown flag, check ID or rule ID is 2. With 2, nothing is fetched (the test confirms that no request reaches the test server)
- With `--format json` and 3, the JSON on standard output contains `could_not_check`. With 2, standard output is empty
- Even when the check ran only partway (a limit was hit, there is `not_fetched`, there is `skipped`), the exit code is decided by the findings alone. The range always appears in both text (the limits on the first line, the `not fetched:`, `limits hit:` and `skipped:` lines) and JSON (`summary.limits_hit`, `summary.not_fetched`, `skipped`) (cli-reference.md §4)

### 2.2 Crawl

- Only the same origin as the start URL (scheme, host and port all the same) is crawled. Subdomains, another port, and http vs. https are all treated as "external".
  If the start URL is redirected, the origin of the final destination is the base (for `http://example.com` → `https://example.com`, the https side is crawled)
- It stops exactly at the depth limit and the page limit (limit - 1, limit, limit + 1)
- Page candidates not followed because of a limit (depth, pages) are still checked for liveness as links (outside the depth limit, with HEAD. The page limit is spent on the pages that turn out to be HTML when fetched, in order, so pages outside that limit are GET too). What the limit bounds is the number of pages whose HTML is read and followed further; every link on a crawled page is checked. The number not followed is `not_fetched.over_limits` (only those known to be HTML: outside the depth limit this is judged from the HEAD's `Content-Type`, so pages from a server that does not send it on HEAD are not counted)
- URLs on the start URL's origin are fetched without verifying the certificate (robots.txt, pages, same-origin links. A certificate problem is said once, by `cert`. cli-reference.md §2.1). When a chain leaves for another origin, it is verified from there on, and a failure is `links.unreachable` (tls)
- If the same link is on several pages, it is fetched once and every place it was found is kept (even at different depths). The exact same reference (URL, element, attribute, value) appearing many times on one page is one (nothing is lost). Against hostile input, one finding keeps at most 100 places (for every rule): JSON `found_on` holds the first 100, and text says how many remain (cli-reference.md §5.1 "folded into a count when there are too many". There is no JSON key that gives the count. The count is taken from the deduplicated set, so it is exact). Before that, when the crawl collects them, it keeps only up to 10000 per URL; beyond that, text does not give a count and says only "there are more" (because when several links have each discarded the same places, the counts cannot be added)
- The page limit is spent on HTML pages only (a 404, a non-HTML response, or a redirect to outside does not consume it). `limits_hit` only when a limit was hit
- The references checked from one page are capped at `--max-links-per-page` (counted by distinct URL; the same URL any number of times is 1). Those beyond it are not fetched; URLs that were not checked from any other page either are counted in `not_fetched.over_limits`, and `limits_hit` gets `max-links-per-page`. The cap bounds the liveness requests that a single page with thousands of links can cause. Exactly at the limit, it is not hit. The "places found" of references beyond the limit are not discarded: if the same URL was checked from another page (before or after), they appear in `found_on`
- Requests to the same host (`host:port`) go one at a time (after the previous response returns, wait `--delay` / `Crawl-delay`, then the next). What `--concurrency` runs in parallel is different hosts. The default of `--delay` is cli-reference.md §3.2
- The gap to a host that sent 429 is widened until the end of that run. New gap = the longest of: twice the current gap, a readable `Retry-After` (when it is 30 seconds or less), and 1 second. The cap is 10 seconds. It widens even if the retry gets 200 (receiving the 429 is itself the signal). It widens before the turn that received the 429 is released (requests that were waiting for the same host also wait the widened gap). Gaps to other hosts do not change. The next request waits the longer of `--delay` / `Crawl-delay` and the widened gap. The 429 retry (once) waits only `Retry-After` (1 second if absent), as in §3.1, and does not use the widened gap (the widened gap applies from the next request). However, if a request that was waiting for the same host takes the turn first, the retry comes after it. The "time waited" that the sentence states is the time that actually passed between receiving the 429 and the retry (it can be longer than the Retry-After). The crawl and the sitemap reading use the same turn: a gap widened by a 429 in the crawl also applies to sitemap requests, and the first sitemap request also waits `--delay` after the crawl's last response ("for the rest of the run" in cli-reference.md §3.2). A 429 on a request that does not go through the turn (the start page, the probe, robots.txt) does not widen the gap (requests that do not go through the turn are a known limitation in discovery.md §2)
- References to private addresses and `localhost` are not fetched. A private address is one that the IANA IPv4 and IPv6 Special-Purpose Address Registries mark as not globally reachable (less the blocks inside it they mark globally reachable, such as `192.0.0.9`, `192.0.0.10`, `2001:1::1`–`2001:1::3`, `2001:3::/32`, `2001:4:112::/48`, `2001:20::/28` and `2001:30::/28`), plus multicast (`224/4`, `ff00::/8`) and `255.255.255.255`: for example loopback (`127.0.0.0/8`, `::1`), private use (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`), `100.64/10`, `198.18/15`, the documentation ranges, `240/4`, link-local and unspecified addresses (`cli-reference.md` §5.2 lists them; an IPv4-mapped IPv6 address is judged as its IPv4 address; `192.88.99/24`, which has no value in the registry, is not private except `192.88.99.2`, and `2002::/16`, N/A, is not private; `2001::/32` (TEREDO, N/A in the registry) and `2001:10::/28` (no value) are private, as tenken's choice, following `2001::/23`). Each range is held at its first and last address and at the addresses just outside it. They are not fetched unless they are the start host (below), and are counted in `not_fetched.private` (because a public site's HTML can point at `http://localhost:8080/` and hit inside the CI machine). The same holds when a host name resolves to a private address: just before connecting, the resolved IPs are checked, and if all of them are private it does not connect and counts it as `private`. If they are mixed with non-private IPs, it connects only to the non-private IPs. It connects to the IP it checked, and does not resolve again between checking and connecting. The connection is made the same way as net.Dialer: IPv6 and IPv4 race (Happy Eyeballs, 300ms), and within one family, the next IP after a silent one is also tried (even if one family is silent, if the other connects it does not say unreachable). If none connects, the failure of the first IP decides the `reason`. If the answer is empty, it is dns, not private. The IPv4-mapped IPv6 forms (`[::ffff:127.0.0.1]`, `::ffff:10.0.0.5` as a resolution result) are the same. It does not say unreachable (`unreachable`): it did not connect. The only exception is the start host: the host of the start URL as the user wrote it (not where it redirects; case-insensitive, without a trailing dot, without the port). Whether it is local is decided once, from the one resolution of the first connection to it (the first response that arrives, a 429 included; the retry of a 429 is sent as that decision says, and does not decide again): a private IP or `localhost`, or an answer that is all private, connects there and makes it local, and its URLs are then fetched even if private for the whole run; an answer with any non-private IP connects only to those, and the start host is not local, so when the same name later resolves only to private addresses (DNS rebinding) it does not connect and counts it as `private`, like any other host. A start host reached through a proxy is not local unless it is a private IP or `localhost`. The TLS connection of `cert` does not resolve the name again either: it goes to the address the start URL's chain connected to (§3.3). The start URL's own chain and the `http://` probe follow the same rule: a redirect into a private address of another host is stopped before it and counted as `private`; for the start URL's own chain the run could not check: exit 3, `could_not_check.code` `private-address` (§2.1). The same holds when the start host itself rebinds within the start URL's chain, with its own reason (§2.1). Requests through a proxy are not checked (what it connects to is the proxy, and the destination cannot be checked). The target of a robots.txt redirect is checked the same way (a local start host is the exception). If the destination is private, it does not connect, counts the destination as `private` (1 even across the crawl and the sitemap), and treats robots.txt as unusable: the crawl stops at the start page, `skipped` is `robots-unavailable`, and if `sitemap` is selected, `sitemap.robots-unreachable` (`reason: redirect`), whose sentence says it was a redirect to a private address (it does not say robots.txt is absent: it could not be obtained). If a redirect target is one, it stops before it and counts it as `private` (what is counted is the URL of the destination not fetched; two chains jumping to the same destination are 1. The chain up to there is looked at by `redirects.*`. `links.*` does not appear: liveness was not checked. For a sitemap URL, `sitemap.url-redirects` does appear: that it redirects was observed). The sitemap files themselves (a `Sitemap:` line in robots.txt, an index's child, `/sitemap.xml`) and their redirect targets are the same: not fetched, counted as `private`, and no finding is emitted (neither `sitemap.invalid` nor `sitemap.missing`: not fetching it is tenken's rule, and the sitemap was not observed to be broken)
- `--max-duration` and `--max-requests` (limits on the whole run. cli-reference.md §3.2):
  - After a limit is hit, no new request is sent. Requests sent before it was hit are finished. If the deadline passes during a `--delay` or 429 wait, the request after the wait is not sent
  - It does not wait for requests it will not send: after a limit is hit, the remaining candidates do not sleep for the same host's turn or `--delay` (if they slept, the run would sleep one gap per remaining candidate and continue past the limit)
  - With `--max-requests`, the crawl fetches one at a time in the order of the candidate URLs: which URLs fall within the limit (and the findings and the exit code) are the same for the same input (§2.3)
  - URLs not fetched count 1 per URL in `not_fetched.over_limits`, and `limits_hit` gets `max-duration` / `max-requests`. The findings up to there are emitted, and the exit code is decided by the findings (0 / 1)
  - A chain stopped by the limit is not made a finding, including the redirects seen partway (none of `links.*`, `redirects.*`, `sitemap.*`). A URL whose 429 retry was not sent because of the limit is not made `links.rate-limited` either (it was not retried, so "429 even after a retry" cannot be said)
  - `--max-requests` counts every outgoing HTTP request (the start page, the probe, robots.txt, the crawl, the sitemap, 429 retries, each hop of a redirect). It never exceeds N, even in parallel. The start page, the probe and robots.txt are counted but not stopped. Certificate checks (only the TLS handshake) are not requests and are not counted
  - `0` is unlimited. If both are `0`, it is as before
- In a crawl without `links` selected, nothing about references is counted: `private` and the excess over `--max-links-per-page` are about references too, so they are not counted (page candidates over a limit are counted in `over_limits`, the same as with `links`)
- A body is read only for a response that could be parsed as a page (a 2xx HTML response that arrived on the same origin). Link liveness checks (HEAD, the GET retry after a 4xx / 5xx HEAD, and the GET of a page candidate alike) and sitemap URL checks cut the connection once the status and headers arrive, without reading the body (if the link target is a huge file, it would otherwise download all of it up to `--max-body`). A body that was read is not kept once its references are extracted either (no body remains in the crawl's result)
- A crawl without `links` selected (for `headers` / `redirects`): references are not checked for liveness (subresources and external links are not fetched, and not counted in `not_fetched` either: they are the denominator of `links`). Page candidates are handled the same (those outside a limit are fetched and counted), so `pages_crawled`, `limits_hit` and `not_fetched.over_limits` do not change with or without `links`
- When robots.txt is unusable and the crawl stops at the start page, the `skipped` (`robots-unavailable`) appears for every selected check that needs the crawl (`redirects` / `links` / `headers`). It speaks about external links only for `links` (the others do not look at external ones)
- robots.txt: how its redirects are followed and how it is handled when unusable is cli-reference.md §2.1. Only its first 500 KiB are parsed (RFC 9309 §2.5); the rest is downloaded up to `--max-body` and ignored, and nothing is reported for either cut. Groups with the same name are combined. `Crawl-delay` is used only for values greater than 0 and less than 1 hour (others are ignored). Not reachable (timed out) is handled the same as 5xx
- Problems with a single-hop redirect met in the crawl (a loop to itself, a broken `Location`) also appear as `redirects.*` (if `redirects` is left out, they do not: they are `redirects` rules)
- The same URL is never fetched twice (including normalisation of a trailing slash, `#fragment`, query order, and letter case)
- Relative URLs, `<base href>`, `../`, and protocol-relative URLs (`//host/path`) are resolved correctly
- `mailto:`, `tel:`, `javascript:` and `data:` are not fetched. Not reported either
- Internationalised domain names and percent-encoded paths are not broken
- The limit on concurrent connections is not exceeded. The per-host gap is kept
- URLs disallowed by robots.txt are not crawled
- A URL that timed out is reported as "unreachable", and the whole run does not stop
- Links are not extracted from huge responses or non-HTML responses (PDF, images)
- Looping links (A → B → A) do not make it run forever

### 2.3 Output

- The same input gives the same output (including order)
- JSON follows the schema. It carries the URL, the kind of check, the severity, the reason, and the places found
- A "place found" is the page URL, the element (tag and attribute, e.g. `img[src]`), and the value of that attribute. No line numbers (the HTML parser is not asked for position information)
- With 0 results, it still comes out in the correct shape
- Standard output and standard error have fixed roles (results on standard output, progress and logs on standard error)
- The version (`--version`, the default User-Agent, `tool.version` in JSON) is the one a release build was given; without one, the module version Go recorded in the binary, without the leading `v` (so `go install …@v0.1.0-dev.1` and the release archive of the same tag say the same `0.1.0-dev.1`); without either (`(devel)`, empty, or no build information), `0.0.0-dev`
- When a request went through a proxy, it says in one line on standard error, at the end of the run, that what the proxy connected to on the far side cannot be checked. Whether it went through is decided by Go (`http.ProxyFromEnvironment`) alone: if the environment variables are set but it did not go through (matched `NO_PROXY`, Go discarded the value, addressed to loopback), it does not say it. tenken does not re-read the environment variables to decide (CLAUDE.md §3: never two answers to the same question). Inside the parentheses is the name of the variable Go uses for requests of that scheme (upper case first). Standard output (text / JSON) and the exit code do not change. A run that does not connect does not say it

## 3. Perspectives per check

The "fail / warn / info" in this section is the rule's default severity, added to make the perspectives easier to read. **The source of truth is cli-reference.md §2.2**, and if they disagree, that one is right.

### 3.1 Broken links

| Perspective | Expected |
|---|---|
| 200 | No problem |
| 404 / 410 / 500 / 503 | fail. Report the status |
| 401 / 403 on another origin | warn (`links.forbidden`. The other side refused: a site on another origin may refuse a client it does not know, which says nothing about whether the link works). 401 / 403 on the same origin is fail (`links.broken`). Which one is decided by the origin of the last response that returned 401 / 403 (if our own URL leaves for another origin by redirect and gets 403, it is warn) |
| Unreachable (DNS failure, connection refused, timeout) | fail. Report with the reasons kept apart |
| A response arrived but cannot be read as HTTP (broken status line or headers, the connection cut in the middle of the headers) | fail (`links.unreachable`, `reason` is `malformed`). For the start URL, 3 (`could_not_check.code` is `malformed`). It is not called `connect` (the connection was made and the first byte came). The judgement is by stage, not by string (a failure after the first byte arrived that is not a timeout) |
| Kinds of link | `a[href]`, `img[src]`, `img[srcset]`, `script[src]`, `link[href]` (stylesheet and the like) are all picked up. But a `link` whose `rel` is `preconnect` / `dns-prefetch` is not (it is the name of an origin, not a resource: its `/` may answer 404 while the origin works) |
| External links | Only whether they are alive. Not crawled beyond |
| Servers that do not accept HEAD, servers that return 4xx only to HEAD | If HEAD is 4xx / 5xx, retry with GET and judge by the GET result (not only 405 / 501: a server may answer 404 to HEAD and 200 to GET). The retry GET does not read the body either. 429 is different (the retry rule is the 429 row in §3.1) |
| 429 (too many) | Not made fail. Wait `Retry-After` (seconds or an HTTP date. A date is one of the three forms in RFC 9110 §5.6.7. If absent, 1 second), retry only once, and if still 429, report it as warn. If `Retry-After` is over 30 seconds, do not wait and treat it the same as "429 even after a retry" (CI is not held up for minutes. cli-reference.md does not decide these two values, so they are decided here) |
| External links and robots.txt | The liveness check of an external link (one HEAD / GET) does not look at the other side's robots.txt. Our own origin's robots.txt applies to the crawl and to the liveness checks of same-origin URLs (disallowed URLs and subresources are not fetched and are counted in `not_fetched`) |
| `retry_after_seconds` of a 429 | If `Retry-After` can be read as seconds or a date, that number of seconds (as is, even if longer than the limit tenken waits). If absent, or unreadable, `null` (cli-reference.md §5.2 only says "`null` if absent". The unreadable case is decided here) |
| The same broken link on several pages | Reported as one, keeping every place found |
| Broken HTML | Parsing does not stop, and the links that can be picked up are picked up |
| An `http://` reference on an https page (static Mixed Content) | warn (the attributes covered are `links.mixed-content` in cli-reference.md §2.2). `a[href]` is not covered, because navigating to a link target is not Mixed Content |

### 3.2 Redirects

| Perspective | Expected |
|---|---|
| One hop | No problem (the final destination is included in the report) |
| More hops than the threshold | warn. The hop-count boundaries (threshold - 1, threshold, threshold + 1) |
| Loop (A → B → A, A → A) | fail. Not followed forever |
| A redirect from https to http (downgrade) | fail |
| http does not go to https | warn. When the start URL is https, access the same host's `http://` once to check (no crawl). When the start URL is http, that it does not itself go to https is the warn (`found_on` is `start`) |
| The same host's `http://` cannot be reached, or 429 even after a retry | No finding; `redirects` appears as `skipped` (`probe-unavailable`). Connection refused included. It does not affect the exit code |
| The start URL's redirects exceed the hop limit | warn (`redirects.too-many`), and in addition the checks that need the crawl are `skipped` (`start-page-broken`) |
| 302 / 307 (temporary redirects) | Reported as info. Whether it "should be permanent" is not something the tool can know, so it is not made fail or warn |
| `Location` absent, broken, or a relative URL | If broken, fail. A relative URL is resolved correctly |
| The redirect target is 404 | Reported as a broken link, with the path shown too |

### 3.3 TLS certificates

| Perspective | Expected |
|---|---|
| More days left than the threshold | No problem |
| Days-left boundaries | The warn threshold - 1 day, exactly, + 1 day. The same for the fail threshold |
| Expired | fail. **Even when verification fails, the expiry date can be reported** |
| Not yet valid (NotBefore in the future) | fail |
| Host name mismatch (not in the SAN) | fail |
| Wildcard (`*.example.com`) match and mismatch (`a.b.example.com` does not match) | Judged correctly |
| Intermediate certificate not sent (an incomplete chain) | fail. It does not fetch intermediates from AIA to fill in (browsers sometimes do, but curl and many libraries fail) |
| Self-signed | fail (default). Passes with the option that names a CA to trust. Still self-signed even if extra certificates are sent with it |
| An intermediate expired or not yet valid as of now (the peer's certificate is valid) | `cert.untrusted` (`invalid-chain`). Regardless of how the dates of the peer's certificate are arranged |
| An intermediate is not a CA (CA:FALSE) but is included in the chain | `cert.untrusted` (`invalid-chain`). If not included, `issuer-not-found` |
| Intermediates are sent, but the one above them is an unknown authority | `cert.untrusted` (`issuer-not-found`) |
| An intermediate with only the same name, which did not sign the peer's certificate (an old one from before a key change) | `cert.untrusted` (`issuer-not-found`) |
| Two intermediates with the same name (one usable but not conforming to the rules, and one from an unknown CA) | The reason is the same even if the order they were sent in is swapped |
| An intermediate from an unknown CA that is broken in other ways too (an unhandled critical extension and the like) | `issuer-not-found` (reaching a trusted CA was not confirmed) |
| A chain whose names loop, a self-signed root sent with no trusted CA | Stops and answers (does not follow forever) |
| An intermediate's dates start before the root's (back-dated), but both are valid now, and the intermediate is not a CA | `invalid-chain`. Whether it reached is looked at at three times: that certificate's "start", "end", and "now (its edge if outside the validity)" ("now" is the time in cli-reference.md §2.2: if the peer's certificate is outside its validity, that edge). No other constructed time is looked at |
| The root is expired as of now, and was valid when the intermediate was issued | `cert.untrusted` (`invalid-chain`) |
| The root is not yet valid as of now, and is valid at the intermediate's end | `cert.untrusted` (`invalid-chain`) |
| The root was issued after the intermediate, is expired now, and the intermediate is still valid | `cert.untrusted` (`issuer-not-found`): it cannot be confirmed at any of the three times (a limitation written in cli-reference.md §5.2) |
| Hundreds of certificates with the same name are sent | There is a limit on the number of signatures checked. If, among the certificates sent, the number of "pairs that could be parent by name" exceeds the limit, none is checked and it is `issuer-not-found` (reaching could not be confirmed). The number of pairs does not depend on the order sent, so neither does the answer: under a trusted root → intermediate → non-CA intermediate S, mix in Sx, signed by an unknown CA with the same name and the same key as S, and N pieces of junk with the same name as Sx's issuer; swapping the order of S and Sx gives the same result (a design where whether the limit is hit depends on the walking order splits the answer here). Self-issued junk (its own name equals its issuer's name) pairs with each other, so mixing 10 with one real intermediate hits the limit, and 9 does not. If the peer's certificate is directly under a trusted CA, it reaches without checking signatures, so the answer comes before the limit however much junk is mixed in. Exactly at the limit, it checks. The time is finite |
| The usage does not fit server authentication | `cert.untrusted` (`invalid-chain`) |
| The peer's certificate is expired, and the chain is trustworthy | `cert.expired` only (no trust finding) |
| A certificate with no SAN | `subject_alt_names` is an empty array (not null) |
| The host checked | Only the start URL's host (after redirects), connected to at the address the start URL's chain connected to: the name is not resolved again, so a name that later resolves to a private address is not connected to (with no checked address — through a proxy, or a local start host connected to without a check — it connects by name as before). However many times the same host is referenced, it is checked once. Certificates of external link targets are not checked (a TLS failure appears as "unreachable") |
| What is not looked at | Revocation (OCSP / CRL), TLS version, cipher suites ([`design.md`](design.md) §0.4) |
| Defaults of the days-left thresholds | The defaults are cli-reference.md §3.2 (`--cert-warn` / `--cert-fail`). The boundaries are tried with 90-day, 47-day and 6-day certificates. When overridden with a number of days, that wins |
| An http-only site | The certificate check appears as "skipped" |

### 3.5 sitemap / robots

| Perspective | Expected |
|---|---|
| No robots.txt (404) | info. The check continues |
| robots.txt is 5xx | warn. Everything is treated as disallowed, and nothing past the start page is crawled. The sitemap is read, but the same-origin URLs in it are not fetched, and are `sitemap.url-disallowed` (the full disallow in cli-reference.md §2.1 applies to sitemap URLs too) |
| robots.txt cannot be reached, or 429 even after a retry | Handled the same as 5xx (`sitemap.robots-unreachable` / `sitemap.robots-rate-limited`) |
| robots.txt's redirects are unusable (a loop, a broken `Location`, more than 5, a redirect to a private address) | Handled the same as 5xx. `sitemap.robots-unreachable` with `reason` `redirect`. | A sitemap URL is 429 even after a retry | warn (`sitemap.url-rate-limited`, `retry_after_seconds`). It does not say broken |
| The sitemap file itself is 429 even after a retry | warn (`sitemap.rate-limited`, `retry_after_seconds`). It does not say broken |
| Sitemap index nesting deeper than `crawl.MaxSitemapNesting` | The deep children are not read, and `limits_hit` gets `sitemap-nesting` |
| A `<loc>` that is not a URL | `sitemap.invalid` for that sitemap (the count and examples in `problem`). The other URLs are checked. Even if it stopped partway at a limit, or the XML is broken elsewhere too, the count and examples go on `problem` |
| A gzip sitemap cut off at `--max-body` | The URLs up to where it could be decompressed are checked, and `problem` is "larger than `--max-body`" (it does not say the gzip is broken) |

| A `<loc>` that is not a URL inside an index | `problem` says "the others were read as sitemaps" (they were not checked as URLs) |
| No `Sitemap:`, and the guessed `/sitemap.xml` is 5xx | `sitemap.invalid` (the response is broken. Only 4xx is `sitemap.missing`) |

| robots.txt is 401 / 403 / 410 and the like (4xx other than 429) | info (`sitemap.robots-missing`). Following RFC 9309, crawled as unrestricted |
| robots.txt `Sitemap:` lines | The sitemaps written there are used. With no line, `/sitemap.xml` is looked at |
| No sitemap.xml | info |
| A sitemap URL is 200 | No problem. Sitemap URLs only have their status looked at; they are not parsed or crawled as pages |
| A sitemap URL returns 4xx only to HEAD | Retry with GET, and judge by the GET result (the same as crawled links. The HEAD row in §3.1). The retry GET does not read the body either |
| A sitemap URL is 404 / redirects | fail / warn |
| The sitemap lists a URL on another origin | warn. Not fetched |
| The sitemap lists a URL disallowed by robots | warn. Not fetched |
| Sitemap index (nested sitemaps) | Followed. Nesting loops do not make it run forever |
| A gzipped sitemap (`.xml.gz`) | Readable |
| Broken XML | Reported as fail, and the whole run does not stop |
| A huge sitemap (over `--max-sitemap-urls`) | Read up to the limit, and `summary.limits_hit` gets `max-sitemap-urls`. It does not exhaust memory |
| A declared sitemap (a `Sitemap:` line, an index's child) is 4xx / 5xx, or cannot be reached | `sitemap.invalid` (the declaration is broken). `sitemap.missing` only when there is no declaration and `/sitemap.xml` is 4xx |
| The `<loc>` read before broken XML breaks | Checked (it does not go silent about what was read) |
| The sitemap lists URLs fetched by the crawl | Not fetched twice (the crawl's result is used) |
| The same URL in several sitemaps (or twice in the same sitemap) | Fetched only once, one finding with every place in `found_on` |
| `--skip` `sitemap` | robots.txt is read for the crawl, but neither `sitemap.robots-*` nor `sitemap.*` appears |
| The start page is 4xx | `sitemap` runs (only the checks that need the crawl are `start-page-broken`) |
| A sitemap URL redirects (with `redirects` also selected) | `sitemap.url-redirects`, and `redirects.*` for that chain (`found_on` is `sitemap`) |
| Claims gzip but cannot be decompressed, a root that is neither `<urlset>` nor `<sitemapindex>`, XML that claims a non-UTF-8 encoding | `sitemap.invalid` (`problem` says what was broken. Library text is not shown) |

| `--max-sitemap-urls` is hit between files (before reading the next `Sitemap:` line or an index's child) | `limits_hit` gets `max-sitemap-urls` (it does not stay silent while there are sitemaps it did not read) |
| A URL matching `--exclude` is in the sitemap, or the sitemap itself matches | Not fetched, counted in `not_fetched.excluded`. No finding |
| `not_fetched` external / robots_disallowed / excluded | 1 per URL (1 even if the same URL is listed twice. cli-reference.md §5.2 "The number of URLs not fetched") |
| A URL the crawl did not fetch (robots.txt disallow or unusable, `--exclude`, another origin, private, not checked because of `--max-links-per-page`) is also in the sitemap | `not_fetched` is 1 per URL even across the crawl and the sitemap. | The sentence of `sitemap.url-disallowed` when robots.txt is unusable | It does not say "disallowed by robots.txt"; it says it was not fetched because robots.txt was unusable (there is no Disallow line) |

## 6. What is implemented (claims and the tests that assert them)

(What is not implemented yet is [`discovery.md`](discovery.md) §2 "Known limitations")

⚠ **A row is added only after the behaviour exists and a check that asserts it has run.** ⚠ **A plan is not an implementation.**

⚠ **"The case that asserts it" is written as the name of the case. Not a file name.** A file name only says where to look;
it does not say that anything in it supports this claim. ⚠ **Before filling a row, run that case and read whether it
covers every clause of the claim.**

⚠ **The grounds**: a row can name two files as "supporting the claim" when neither of them supports it, and a gap
already written in a completion report does not stop the row from staying as it is.
⚠ **Having stated a gap in one place is no reason to claim it in another.**

⚠ **What a static check can stop: a row with only a file name and no case, a row that names nothing, a case name that does not exist.**
⚠ **That an existing case does not cover a clause is something a machine cannot stop** — reading that is the review's job,
and that is where it gets skipped. ⚠ **Write that check early** (in the `verify` skill).
